# testing/ — PutnamBench-60 held-out harness

(ported from rocq-mcp-evolve; this file itself is new — it plays the role of
rocq-mcp-evolve's top-level README + `configs/FROZEN.md` intro combined for
this harness, with the same "Rocq -> Lean" mapping tables PORT_SPEC.md asked
for)

## Purpose

This is the Lean/PutnamBench-60 twin of rocq-mcp-evolve's miniF2F held-out
harness. **Principle (user requirement, PORT_SPEC.md): the SET-UP and the
PROMPTS are exactly the same as the Rocq miniF2F held-out tests** — same
harness code paths, same policy (`claude` CLI headless, MCP tools only,
`--tools "" --allowedTools ...`, stream-json), same budgets (`max_turns`,
`attempt_timeout_s 300`, reps, parallel), same gate layering, same prompt
texts with ONLY the language-specific words substituted (table below). Every
difference from rocq-mcp-evolve is listed in the Deviations table at the
bottom, with the reason.

Twelve arms are evaluated on 60 PutnamBench problems (20 easy / 20 medium /
20 hard, `dataset/manifest.json`), each problem run twice (opus arms once),
mirroring rocq-mcp-evolve's `FINAL_*` held-out matrix.

**Source branch**: everything here was ported from the `dev` branch of
`rocq-mcp-evolve-private` at commit `4688cd9` (2026-09-03, "Merge main (A128
consolidation, A129 logs release) into dev"), read from a clean checkout of that
branch. At that commit the only differences between `main` and `dev` under `harness/`,
`configs/`, `src/baseline_server/`, `src/submit_server/`, `src/mcp_core/` and
`docs/ASSUMPTIONS.md` are three items present on `main` only (`configs/team_k3.json`,
`harness/run_team.py`, one 13-line trail entry) — a team-runner experiment that is
not part of the miniF2F held-out matrix. Every file this port derives from is
byte-identical on both branches; `dev` is the reference.

**Requirements**: Python ≥ 3.10 (the harness uses `X | None` annotations, as the Rocq
harness does; macOS's `/usr/bin/python3` is 3.9 and fails at import — put a 3.10+
`python3` first on `PATH`), the elan toolchain (`~/.elan/bin`), the `claude` CLI, and
the built binaries `.lake/build/bin/{lean-mcp-evolve,gate,lean-mcp-baseline,lean-mcp-submit,lean-mcp-files}`
(`lake build lean-mcp-evolve gate lean-mcp-baseline lean-mcp-submit`).

## Gate mapping (section 7)

| Rocq `gate.py` layer | Lean `gate.py` layer |
|---|---|
| 1. prefix lock (`split_at_prefix`, whitespace-normalized) | same algorithm, unchanged |
| 2. region lock: strip `(* *)` comments + string literals, FORBIDDEN regex scan | strip `--`/`/- -/` comments + string literals (backslash-escaped, not doubled-quote); FORBIDDEN list: `sorry, admit, axiom, native_decide, set_option, run_tac, run_cmd, #eval, #exit, unsafe, implemented_by, extern, ofReduceBool, ofReduceNat, sorryAx, addDecl, addDeclWithoutChecking, Lean.Elab, Lean.Meta, Lean.Environment, Lean.Kernel, +native, import` |
| 3+4. shell out to `rocq compile` (+ `-ri` module injection) directly, then `Print Assumptions` | shell out to the built `<repo>/.lake/build/bin/gate <cand> --theorem <t> --reference <task.lean> --project <proj> --json` binary, which does fresh recompile + presence/type check + axiom audit + **kernel replay** (no Rocq analogue — stronger) in one process |
| reasons: `prefix_modified`, `forbidden_token:<label>`, `recompile_failed`, `assumption_audit_failed`, `assumption_parse_failed`, `unsafe_flags`, `target_is_axiom` | reasons: `prefix_modified`, `forbidden_token:<label>`, `gate:<binary reason>` (e.g. `gate:compile_error:...`, `gate:axiom:sorryAx`, `gate:statement_modified`, `gate:suffix_modified`, `gate:kernel_replay_failed:...`), `gate_unavailable` (no JSON on stdout), `recompile_timeout` |
| `timeout_s=120` | `GATE_TIMEOUT_S=300` (env-overridable) — **DEVIATION**: the Lean gate loads Mathlib (~10-30s) and kernel-replays; Rocq's 120s budget would false-fail routinely. |
| prefix lock is whitespace-normalized only | the gate BINARY *also* enforces byte-level prefix/suffix equality against `--reference` (statement/prefix/suffix, tolerating exactly one extra `import Mathlib.Tactic` line) — **STRICTER than Rocq's own lock**, see Deviations. |

## Arm: autoformalization tool surface on the proving task

`session_af_tools_sonnet_wallonly` (config_id, AF_TOOLS_SPEC.md, added
2026-09-07 — user decision) reruns the `medium5_test` test (same 5 theorems,
`claude-sonnet-5`, 1 rep, 300s wall, 200-turn rail — SAME prompts and budgets
as `session_try_hints_auto_sonnet_wallonly`, see above) but replaces the
5-tool session interface with the tool surface of the Rocq autoformalization
arm `af3_evolve` (`rocq-mcp-evolve-private/configs/af3_evolve.json`): the
files sidecar (`write_file`, `read_file`, `list_dir`, `lake_build`, `verify`
— `testing/servers/Files.lean`, `lean_exe lean-mcp-files`, a port of
`src/files_server/rocq_agent_files.ml`) **plus** ALL NINE prover tools
(`open`, `build`, `check`, `step`, `try`, `auto_close`, `state`, `rollback`,
`verify` — `LEAN_ENABLE_TOOLS` left unset, the server's own default), and a
per-problem Lake project the model can create and manage files in.

**What/why**: the guided evolve interface only ever showed the model a live
in-session goal (`step`/`try`/`auto_close`/`state`/`rollback`); this arm
additionally gives it a real filesystem sandbox and the file-level tools
(`open`/`build`/`check`/`verify`) the Rocq autoformalization measurement
used, to see whether a wider, file-centric tool surface changes solve rate
on the SAME 5 problems under the SAME budget — isolating the tool-surface
variable from every other configuration difference (A80-style fair
integration, one variable at a time).

**Workspace layout** (`run_eval.py`, `cfg["workspace"] == "lake_putnam"`,
AF_TOOLS_SPEC.md section 2): a fresh `<attempt>/workspace/` Lake project per
attempt —

```
workspace/
  lean-toolchain      copy of <PROJECT>/lean-toolchain
  lake-manifest.json  copy of <PROJECT>/lake-manifest.json, "packagesDir"
                       REWRITTEN to the ABSOLUTE "<PROJECT>/.lake/packages"
  lakefile.toml       name = "putnam_ws"; packagesDir = "<PROJECT>/.lake/packages";
                       [[require]] mathlib rev = <PROJECT's lakefile.toml rev>;
                       [[lean_lib]] name = "Putnam" globs = ["Putnam.+"]
  Putnam/<problem_id>.lean = the dataset file verbatim (task.lean)
```

The `packagesDir` rewrite is SAFETY CRITICAL: without it, `lake build` in the
workspace does not see `<PROJECT>`'s already-fetched/built Mathlib as a
sibling and instead clones + rebuilds Mathlib from scratch under the
workspace (verified 2026-09-07: a 4 GB clone in progress, killed, before the
rewrite was added). With the rewrite, `lake build` in a fresh workspace
completes in ~15s warm (7745 jobs, only the task file itself is actually
compiled — the dry-run check below measured 15.2s) and writes nothing into
`<PROJECT>/.lake/packages`. The `claude` CLI's cwd for the attempt is the
workspace (mirroring `rocq-mcp-evolve`'s `harness/run_autoform.py`, which
sets `cwd=ws`). The "lean" server gets `LEAN_PROJECT_ROOT=<workspace>` and
`LEAN_TASK_FILE=<workspace>/Putnam/<id>.lean` (instead of `<PROJECT>` and
`<attempt>/task.lean` as the guided arms use) plus the usual
`LEAN_WORKDIR=<attempt>/work`; the "files" extra server additionally gets
`LEAN_WORKSPACE=<workspace>`. `task_prefix.lean`/`task.lean` are still
written to `<attempt>/` exactly as in every other arm, and the prompt
`{prefix}` slot is unchanged — the model sees the same task text either way,
only its tools and its ability to also edit a real file differ.

**Grading order** (`run_eval.py`, AF_TOOLS_SPEC.md section 3; recorded per
row as `"artifact"`): (a) `<workspace>/Putnam/<id>.lean`, if the model edited
it in place (bytes differ from the shipped `task.lean`) — graded via
`gate.check(candidate=<that file>, reference=<attempt>/task.lean,
project=<workspace>)`; (b) else `<attempt>/work/candidate.lean` (an
in-session completion written by the `lean` server exactly as in every other
arm), graded the same way; (c) else `no_candidate`. If (a) exists but is
REJECTED and (b) also exists, (b) is graded too and an ACCEPTING verdict from
either artifact wins — `"artifact"` records which one: `"workspace_file"`,
`"candidate"`, or `null` (no accepted artifact). The gate binary itself runs
with `--project <workspace>`, so its `LEAN_PATH` comes from `lake env` in the
workspace (which resolves to `<PROJECT>`'s shared Mathlib via the same
`packagesDir` rewrite).

**Caveats**:
- Helper lemmas written to EXTRA files in the workspace cannot be imported
  by the delivered target file — the gate's `--reference` check locks the
  target's own import list against the shipped `task.lean`'s. Extra `.lean`
  files are therefore scratch/exploration space only; the delivered proof
  (workspace file or `candidate.lean`) must be self-contained.
- The system prompt is kept byte-identical to
  `session_try_hints_auto_sonnet_wallonly`'s on the user's explicit
  instruction ("keep the other configuration"), so it still describes only
  the five frozen session tools by name. The other nine tools (the files
  sidecar and the four extra prover tools `open`/`build`/`check`/`verify`)
  are documented to the model ONLY by their own shipped MCP tool
  descriptions, discovered via the standard `tools/list` handshake — not by
  any prompt text. This is a deliberate deviation from the Rocq af3 arms,
  which were prompt-free (`system_prompt: ""`) with the server's own
  `README.md` injected into the task prompt as a `{readme}` slot instead;
  that alternative protocol is not used here (see deviation 17).

## Arms: compiler-only control and lean-lsp-mcp sibling in the workspace setting

`af_compiler_only_prompted_sonnet_wallonly` and
`af_lean_lsp_mcp_prompted_sonnet_wallonly` (config_ids, TWO_ARMS_SPEC.md,
added 2026-09-08 — user request) both derive from
`session_af_tools_prompted_sonnet_wallonly` (same model, `max_turns` 200,
`attempt_timeout_s` 300, `"workspace": "lake_putnam"` per-attempt Lake
project, files sidecar behind the prewarm proxy, workspace-file-then-
candidate grading) and each swap ONE Rocq autoformalization arm's tool
surface in for the "lean" nine-tool session, isolating that variable the
same way `session_af_tools_sonnet_wallonly` isolated the tool-surface
variable on the guided proving task:

| arm | what it sees | mirrors (Rocq) |
|---|---|---|
| `af_compiler_only_prompted_sonnet_wallonly` | ONLY the files sidecar (`write_file`, `read_file`, `list_dir`, `lake_build`, `verify`) — no live prover, no MCP server named "lean" at all; the compiler is the only feedback loop | `af3_base` (files sidecar only) |
| `af_lean_lsp_mcp_prompted_sonnet_wallonly` | the files sidecar PLUS `lean-lsp-mcp` (23 tools, pinned `lean-lsp-mcp@0.30.0`) bound to the attempt's own workspace | `af3_sota` (files sidecar + the SOTA sibling `rocq-mcp`) |

**Prompts**: both texts live in `harness/port_configs.py`
(`AF_COMPILER_SYSTEM_PROMPT` / `AF_LSP_SYSTEM_PROMPT`, and the shared
`AF_NOSESSION_TASK_PROMPT`). Unlike the Rocq af3 arms — which were
prompt-free (`system_prompt: ""`) with the server's own README injected into
the task prompt as a `{readme}` slot — both new arms stay PROMPTED, in the
shape of `session_af_tools_prompted_sonnet_wallonly`'s system prompt: the
role sentence, the workspace-tools (`files`) paragraph, the scratch-files
sentence and the strict rules are kept BYTE-IDENTICAL across the base arm
and both new arms.
- `af_compiler_only_prompted_sonnet_wallonly`: the "Prover tools (lean)"
  paragraph is REMOVED (there is no prover) and the workflow paragraph is
  rewritten for the compiler-only loop ("read the file, write your proof in
  place of `sorry` with write_file, lake_build, read the errors, fix,
  repeat; call verify before replying DONE").
- `af_lean_lsp_mcp_prompted_sonnet_wallonly`: the "Prover tools (lean)"
  paragraph is REPLACED by a "Prover tools (leanlsp)" paragraph naming the
  real lean-lsp-mcp tools and what they do (`lean_goal`/`lean_term_goal`,
  `lean_diagnostic_messages`, `lean_hover_info`, `lean_completions`,
  `lean_multi_attempt`, `lean_run_code`, the five search tools, `lean_verify`,
  `lean_build`, `lean_file_outline`, `lean_declaration_file`), written FROM
  `harness/lean_lsp_mcp_readme_excerpt.md` (fetched from
  github.com/oOo0oOo/lean-lsp-mcp's README + `docs/tools.md`, 2026-09-08) and
  the captured handshake's own tool descriptions — not injected into the
  prompt verbatim as a `{readme}` slot the way `af3_sota` did (a deliberate
  choice: the paragraph is a curated summary sized for the system prompt,
  not the whole README; see the excerpt file itself for the untouched
  source). The workflow paragraph is rewritten for the LSP loop: edit the
  proof in place with `write_file`, use `lean_goal`/`lean_diagnostic_messages`
  to see goals and errors, `lean_multi_attempt` to screen candidate tactics,
  the search tools for lemmas, then `lake_build` and `verify` before DONE.

Both arms' task prompt is `AF_TOOLS_TASK_PROMPT` (the base arm's) with the
clause "; the theorem is already open in the prover session and its goal is
shown by state{}" removed (deviation 19) — neither arm has a live session in
that sense; the grading rules, the `{task_file}` placeholder, the prefix
block and "call verify{} before replying DONE" are otherwise unchanged.

**lean-lsp-mcp version**: `af_lean_lsp_mcp_prompted_sonnet_wallonly` pins
`lean-lsp-mcp@0.30.0` in the `uvx` args (`uvx lean-lsp-mcp --version` at
config-generation time: `0.30.0`, matching the captured handshake's
`serverInfo.version` in `lean_lsp_mcp_handshake_cache.json` — see deviation
20). `lean_lsp_mcp_fair_sonnet` and the `af_pf_lean_lsp_mcp*` arms are
UNPINNED (plain `lean-lsp-mcp`) — this port only pins the newest sibling arm;
re-pinning the older three is left for a future change if a version drift is
ever observed.

**`LEAN_PROJECT_PATH`**: `af_lean_lsp_mcp_prompted_sonnet_wallonly`'s server
env sets `"LEAN_PROJECT_PATH": "{workspace}"` — the new `{workspace}`
placeholder (deviation 19), substituted by `run_eval.py` with the attempt's
own `<attempt>/workspace/` dir (the same Lake project `lean-lsp-mcp` should
diagnose the task file inside). `lean_lsp_mcp_fair_sonnet` still hardcodes
`LEAN_PROJECT_PATH` to the shared `LEAN_2026` project (it has no per-attempt
workspace — `project_task_copy`/`prefix_prepend` is its bridge instead); the
two mechanisms are not interchangeable, they solve the same LSP-needs-a-real-
project problem for two different arm shapes.

**Validated against a real workspace** (2026-09-08, before this arm's first
real run): `lean-lsp-mcp` never edits files itself (its own `instructions`
string says so — the files sidecar is load-bearing for it, not optional);
`file_path` is workspace-root-relative; line/column are 1-indexed (columns
count codepoints); an edit made via `write_file` is picked up by the very
NEXT `lean_*` call with no reload/restart needed (~0.1s); no prior
`lake build` of the target file is required for diagnostics to work. The
single most important finding: the dataset ships each theorem's hole as a
TERM-mode `:= sorry` (no `by`) — at that position `lean_goal` returns
`no_goal_at_position` and `lean_multi_attempt`'s tactic snippets fail with
`"Unknown identifier"` (tactic names parse as bare terms in term position).
The system prompt's workflow paragraph therefore tells the model to FIRST
rewrite the hole via `write_file` to `:= by` with an indented `sorry` line,
so `lean_goal`/`lean_multi_attempt` see a real tactic goal from then on;
`lean_diagnostic_messages` works on the raw term-mode file either way. Also
budget the ~10-20s Mathlib-import cost of the first `lean_diagnostic_messages`
/`lean_goal`/`lean_multi_attempt`/`lean_run_code` call against the 300s
attempt wall (cold: ~21s; a machine with the OS page cache already warm on
Mathlib's `.olean`s from a prior attempt: ~9s) — the same cost every
`"workspace": "lake_putnam"` arm already pays on its first tool call.

**No submit sidecar, no `project_task_copy`/`prefix_prepend`** for
`af_lean_lsp_mcp_prompted_sonnet_wallonly`: unlike `lean_lsp_mcp_fair_sonnet`
and the `af_pf_lean_lsp_mcp*` arms (whose deliverable is whatever gets
`submit`ted, since they have no project of their own to edit in place), the
workspace here IS the project lean-lsp-mcp is bound to, so the model edits
`Putnam/<id>.lean` directly and delivery/grading is the workspace file, exactly
like every other `"workspace": "lake_putnam"` arm (workspace file first, then
the absent session's `candidate.lean` fallback — which in practice is always
empty for these two arms, since neither has a "lean" session server that
could write one; `"artifact"` will read `"workspace_file"` or `null`).

### Prompt-diff audit

`harness/port_configs.py` self-audits every generated config: after
applying the substitution table forward, it applies the SAME table
BACKWARDS (new -> old, reverse row order) to the generated Lean text and
asserts the result is byte-identical to the Rocq source text. This is a
mechanical proof that the only spans that differ between each Lean prompt
and its Rocq source are exactly the table's rows — see the script's
printed `audit: OK` line per config (12/12 passed when last generated).

## Resolved issue (2026-09-06): binaries launched outside `lake env` could not see Mathlib

The first smoke runs of this harness (`logs/runs/smoke_baseline`, `smoke_frozen`)
failed for an infrastructure reason: `run_eval.py` starts the MCP server and the
gate directly (the way the Rocq harness starts its OCaml servers), i.e. without
`LEAN_PATH`/`LEAN_SYSROOT` in the environment and from a cwd outside any Lean
project. Under those conditions

- `lean-mcp-evolve`'s `open` refused **every** dataset file (and a trivial
  `import Mathlib` control) with "declaration ... is pattern-matching decl (or has
  no single proof position)": `Text.findDecls`'s header processing imported
  `Init` from elan's default toolchain (`lean --print-prefix` resolved v4.33.1,
  the project is v4.27.0-rc1) and Mathlib not at all, so the statement parsed
  degenerately;
- the `gate` binary rejected valid proofs with
  `compile_error:...: error: unexpected token '+'; expected ':=', 'where' or '|'`
  for the same reason (the REPL's `processInput` re-reads the search path from
  the environment, so `Gate.setupSearchPath`'s programmatic entries were not
  used).

Verified diagnosis: exporting `LEAN_PATH` (or wrapping either binary in
`lake env` from the project) made both work unchanged.

Fix, in the product rather than in the harness: `LeanMcpEvolve/Reexec.lean`
gives both executables a startup bootstrap — if `LEAN_PATH` is unset and a
project root is known (`--project` / the candidate's lakefile ancestor for the
gate; `LEAN_PROJECT_ROOT` / the `LEAN_TASK_FILE` preset's lakefile ancestor for
the server), the binary re-executes itself as `lake env <self> <argv>` from that
root, forwarding stdio and the exit code (`LEAN_NO_REEXEC=1` opts out and guards
the child). After the fix: the control theorem opens and closes through
`auto_close` from the harness environment, `test/test_gate.py` passes 8/8, and
the smoke runs (`logs/runs/smoke_baseline`: sonnet, 1 `check` call, gate
ACCEPTED; `logs/runs/smoke_frozen`: haiku, `state` + one `try` batch, gate
ACCEPTED, axioms `propext`/`Quot.sound`/`Classical.choice`) solve
`putnam_1977_a3` end to end. The harness itself needed no change.

A second, independent parser issue surfaced by the `open` survey
(`harness/open_survey.py`, run after the bootstrap fix): 55/60 files opened,
and the 5 refusals (`putnam_1990_a1`, `putnam_1963_a3`, `putnam_1969_b4`,
`putnam_1989_b6`, `putnam_2017_b6`) were files whose statement uses a
*scoped* notation activated by a standalone `open` command earlier in the
file (`open Nat` for `n !`, `open scoped Real` for `π`). `Text.findDecls`
parses without elaborating, with a fixed parser context, so those `open`s
never took effect and the declaration parsed without a body ("pattern-matching
decl" refusal). Fix in the product: `findDecls` now applies `open`/`namespace`
commands to the parser scope as it goes (see the entry in `docs/PLAN.md`
Status). Re-run the survey after any change to `Text.lean`; it must report
60/60.

### Per-attempt substrate overheads (measured 2026-09-06, warm cache)

These are inside the 300 s wall budget for the agent, exactly as the Rocq
server's (millisecond) startup was, and are the main reason the two substrates
are not equally generous under an identical budget:

| step | Lean (this harness) | Rocq (miniF2F harness) |
|---|---|---|
| server start + `import Mathlib` + statement elaboration (first tool call) | ~35-40 s (12-16 GB RSS) | ~0.1 s |
| baseline `check` compile of a whole file | ~10-40 s | ~1-5 s |
| gate (fresh compile + axiom audit + kernel replay), outside the budget | ~100 s (11 GB RSS) | ~2-10 s |

Consequence: `--parallel` is memory-bound to 1-2 here (deviation 15), and an
attempt's first ~40 s are toolchain load, not proving.
